## 1. Cell B billing: the free Shopify Subscriptions app can bill ONE thing, and that is what we sell

**The conflict.** The Shopify build said the free Shopify Subscriptions app bills only plans created in its own UI, so a selling plan with a fixed first-cycle price can't be used, and implemented cell B as the $25 founding plan plus a first-payment-only $13-off code `STARTER12`. The app build assumed a `bundle_m12` row on its own fixed-first-cycle selling plan (`selling_plan_id 7000000012`).

**What the docs say.**
- A subscription contract is "registered to" one app (`SubscriptionContract.app`: "The subscription app that the subscription contract is registered to"), and billing is that app's job: "Automate billing: The app should provide the automation for billing and renewing subscriptions" ([Model a subscriptions solution](https://shopify.dev/docs/apps/build/purchase-options/subscriptions/model-subscriptions-solution); [SubscriptionContract](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/SubscriptionContract)). Contracts created from Shopify Subscriptions' plans are billed by Shopify Subscriptions; contracts created from a plan our app wrote with `sellingPlanGroupCreate` would be ours to bill, with a scheduler we have not built.
- The Shopify Subscriptions app's plan editor offers three discount shapes, "percentage off, amount off, or fixed price", and a weekly/monthly/yearly delivery interval; there is no first-order-only or first-N-cycles option on the plan ([Shopify Help: Shopify Subscriptions plans](https://help.shopify.com/en/manual/products/purchase-options/subscriptions/shopify-subscriptions/manage-subscriptions/add-edit-plans)). A "fixed price" plan discount applies to every cycle, so it cannot express "$12 then $25".
- Selling-plan pricing policies (fixed then recurring `afterCycle`) exist on the Admin API ([SellingPlanRecurringPricingPolicy](https://shopify.dev/docs/api/admin-graphql/2026-07/enums/SellingPlanPricingPolicyAdjustmentType): "It applies after the fixed pricing policy… afterCycle"), but "the price of the line item does not update automatically" ([About subscription contracts](https://shopify.dev/docs/apps/build/purchase-options/subscriptions/contracts)): the owning app must apply them. That is the app engine, not the launch path.
- Discount codes carry `recurringCycleLimit`: "The number of billing cycles for which the discount can be applied, which is useful for subscription-based discounts", plus `appliesOncePerCustomer` ([DiscountCodeBasicInput](https://shopify.dev/docs/api/admin-graphql/2026-07/input-objects/DiscountCodeBasicInput)); the admin exposes the same as Purchase type → Subscription and "Limit discount to the first payment" ([Help: amount off](https://help.shopify.com/en/manual/discounts/discount-types/percentage-fixed-amount)).

**Decision (implemented).** Cell B = the founding variant on the Shopify Subscriptions app's own "Monthly, renews until you cancel" plan + the code **STARTER12** ($13 off, subscription purchases only, `recurringCycleLimit: 1`, `appliesOncePerCustomer: true`, scoped to the founding product). After the founding close the standard product carries **STARTER12S** ($23 off → $12, then $35). The displayed price is the charged price: the product page's starter view says "$12 today, then $25 a month", the checkout total is $12, and the contract renews at the plan price. A returning customer who already used the code sees the plain price at checkout, never a second $12 month. The fixed-first-cycle selling plan survives only behind `SUBSCRIPTION_ENGINE=app` (shopify/ app engine) and is not the launch path.

**Changed.**
- `shopify/config/catalog.ts`: `DISCOUNTS` gains `STARTER12S` and a per-code `product`; `FUNNEL_ARMS` = B default (`default: true`), A test; comments explain the mechanism. `shopify/src/plan.ts`: the verify export writes `bundle_m12` (and `bundle_m12_standard`) as rows sharing the founding/standard variant + plan with `discount_code`; every row gets `product_handle`.
- `shopify/theme/sections/main-product-membership.liquid`: the `?view=starter` offer works on the standard product too (STARTER12S); the comment states the mechanism. `shopify/theme/layout/theme.liquid` + `assets/strong-years.css`: arm B is the no-JS default and the default when `cells.test === false`; the theme stores a `vid` query parameter so the members app's visitor id survives into the order.
- `app/src/lib/billing/shopify.ts`: `ShopifyProductRow` gains `product_handle` and `discount_code` (migration `app/supabase/migrations/20261001120000_shopify_cell_b_integration.sql`); `matchLine(rows, variant, plan, discountCodes)` prefers the row whose code is on the order, else the row without one; `DEMO_CATALOG` mirrors the real shape; `FRONT_END_CELLS` default `m12,e12`, `FRONT_END_DEFAULT_CELL=m12`; `SHOPIFY_API_VERSION` default `2026-07`.
- `app/src/lib/billing/shopifyWebhook.ts`: `orders/paid` passes the order's `discount_codes` to `matchLine`; the cell-B order records a $12 `membership_charge`, a founding membership at `price_cents 2500`, `price_cell m12`, books included.
- Tests: `app/tests/unit/R10.shopify-webhooks.test.ts` (code → `bundle_m12`; no code → `founding_monthly`; a code never re-maps a one-time line), `R10.launch-waitlist.test.ts` (displayed = charged: cell-B rows share variant + plan with the founding row), `shopify/test/plan.test.ts` (STARTER12 / STARTER12S shapes).

**Also fixed on the way: the redirect itself.** "Selling plans don't work with cart permalinks" ([Create cart permalinks → Limitations](https://shopify.dev/docs/apps/build/checkout/create-cart-permalinks)). The app's `/join` built `/cart/<variant>:1?selling_plan=…`, which would have put a one-time $25 line in the cart. `/join` and `/b` now 302 to the **product page** (`product_handle`), through Shopify's `/discount/<code>?redirect=…` share link for cell B so the code is on the checkout before the visitor ticks anything; the theme's offer form adds the selling plan, records consent (`sy_consent_*`) and re-applies the code. Attribution and the visitor id travel as query parameters the theme stores and writes as cart attributes.

## 2. Webhooks and contract control: store-wide topics are the truth, contract topics are enrichment

**What the docs say.** Every `subscription_contracts/*`, `subscription_billing_attempts/*` and `subscription_billing_cycle*` topic "Requires the read_own_subscription_contracts scope" ([WebhookSubscriptionTopic](https://shopify.dev/docs/api/admin-graphql/2026-07/enums/WebhookSubscriptionTopic)), and the `SubscriptionContract` object and its mutations "Require the read_own_subscription_contracts or write_own_subscription_contracts scope" — *own*: the subscribing app's contracts. The scopes page lists `read_own_subscription_contracts` / `write_own_subscription_contracts` as the subscription-app scopes and makes the Subscriptions APIs a protected access request ([Access scopes](https://shopify.dev/docs/api/usage/access-scopes)). `orders/*`, `refunds/create`, `customers/*`, `inventory_levels/update` and `app/uninstalled` require only `read_orders` / `read_customers` / `read_inventory` and fire for every order in the store, including the renewal orders Shopify Subscriptions creates (`source_name` contains `subscription`). There is no `orders/refunded` topic; `refunds/create` is the refund event.

**Decision (implemented).**
- `shopify/config/webhook-topics.json` is the single contract. `catalog.ts` imports it; provisioning registers exactly `core` (7 topics) and, only in the app engine, `enrichment` (9 topics). `ORDERS_CREATE`, `ORDERS_UPDATED`, `CUSTOMERS_CREATE` were dropped (the app never handled them); `orders/refunded` was dropped from the app (not a topic); `orders/cancelled` and `customers/delete` gained handlers.
- Contract tests on both sides: `shopify/test/plan.test.ts` ("webhooks: exactly the fixture's core topics…") and `app/tests/unit/webhook-contract.test.ts` (fixture == `SHOPIFY_TOPICS_CORE` / `SHOPIFY_TOPICS_ENRICHMENT`, in order).
- `orders/paid` with a renewal `source_name` now **extends `current_period_end` by one period** (idempotent per line), clears grace and reactivates `past_due`/`paused`/`canceled` rows. A cancel or pause made on Shopify's account page is seen as the absence of the next renewal order: access runs to the period end (+ grace after a failure we learn about) and lapses. Contract and billing-attempt events still refine status when they arrive (app engine) but never grant or revoke access alone.
- `shopifyAdmin().cancelContract` refuses unless `SUBSCRIPTION_ENGINE=app`; the 14-day refund and the refund webhook open a ticket ("cancel the contract in Apps → Subscriptions") instead of pretending. The refund email says the subscription is being closed on our side within a business day (weeks before any renewal), not "cancelled".

## 3. Post-purchase: default = cell B, test = cell A, the app stays off

**What the docs say** ([About product offers](https://shopify.dev/docs/apps/build/checkout/product-offers)): "Post-purchase checkout extensions are in beta… To use post-purchase extensions on a live store, you need to request access"; the page "won't be surfaced" when the customer pays with "Klarna, Affirm, AfterPay, Apple Pay, Amazon Pay, or Google Pay", with a gift card or "any payment method other than a credit card", or with providers that retain CVV (PayPal Payments Pro…); and "If the customer's checkout results in the creation of an order without a shipping address, then you can't add a subscription to the order using post-purchase. For example, a customer might have bought only digital products".

**Decision (implemented).** CANON UPDATE 3 in BRIEF.md: **launch default = cell B** (one purchase: $12 today = books + the first founding month, then $25/mo); **cell A = the test cell** ($12 books only, founding offer on the thank-you page + 3 emails); the post-purchase app stays scaffolded in `shopify/app-postpurchase/` but off by default (not a launch prerequisite). Changed: BRIEF.md (CANON UPDATE 3), OFFER.md §0.1, FUNNEL.md (§4.19 and the launch link rule replacing the blitz-mode rule), the app's `FRONT_END_DEFAULT_CELL=m12`, the theme (arm B default), ORGANIC_ENGINE.md §0/§3, and the model: `tools/organic_engine.py` now runs cell B as R20 (default) and cell A with the post-purchase page off as R22 (test); `tools/organic_sheet_refresh.py` rewrote `economics.xlsx` `Organic_First` and `mrr_blitz_daily.csv` (r20…r26); BLITZ.md §0 rows R20–R26 and all of §13 carry the new numbers (R20 $2.1K / $4.6K / $9.0K on days 4 / 14 / 30, retained $4.6K; R22 $0.5K on day 30; R23 $10K on day 6, $50K on day 26, $100K on day 59 at −$185K).

## 4. Essentials save offer: a request with a 1-business-day SLA, no dark patterns

Shopify Subscriptions' customer page lets a member pause, skip or cancel, not swap products; our Admin token can edit only contracts our app owns (§2). `app/src/app/app/account/cancel/page.tsx` in Shopify mode now shows exactly one save offer, **"Switch to Essentials, $12 a month"**, beside an equal-size **"Finish canceling"** that links straight to the Shopify account page (the e2e test measures both buttons). The account page's "Cancel, pause or pay less" button now goes to our cancel page first.

## 5. Renewal reminders: re-check, then conditional wording

`runReminders` (`app/src/lib/billing/clock.ts`) calls `renewalCertainty()` before every reminder: skip when the latest membership charge is refunded or the period already ended without a renewal order; "certain" only when our app owns the contract; otherwise "unsure", and the email reads "If your membership is still active, it renews on … at $25… If you already cancelled or paused it on your account page, nothing is charged and you can ignore this email", linking to Shopify's account page. The first cell-B reminder says the $12 starter month ends and the first $25 charge follows. Shopify Subscriptions' own 3-day reminder stays on as well (LAUNCH_RUNBOOK.md step 14).
